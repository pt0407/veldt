# Veldt v0.2 — Self-Growing Garden, IDE, and Practical Language

## Overview

Veldt v0.1 established the core: code is alive, competes, and dies. But the garden only grows when you manually plant seeds. v0.2 makes the garden **self-evolving**, specifies a **dedicated IDE**, and adds the language features needed to **actually build things**.

## Part 1: Self-Growing Garden

### The problem

Right now, `grow` is the only way code enters the veldt. The ecosystem ages and kills, but it never creates. A garden that only dies is not alive — it needs to seed itself.

### Evolution cycles

New command: `veldt evolve [N]`

Runs N evolution cycles (default 1). Each cycle:

1. **Mutation** — Pick healthy functions and create mutated variants:
   - **Constant mutation**: change numeric constants (e.g., `x * 2` → `x * 3`)
   - **Operator mutation**: swap operators (e.g., `+` → `-`, `<` → `<=`)
   - **Statement swap**: reorder two adjacent statements
   - **Body graft**: take a statement from one function and insert it into another with compatible signatures
   - **Dead code removal**: remove a statement and see if the function still passes its tests
   - Each mutation creates a new variant in the lineage (e.g., `fib#3`)

2. **Trial** — Every new mutant gets a birth trial (same as v0.1):
   - If it has inline tests, run them
   - Otherwise, safe defaults
   - Mutants that crash → sick, short lifespan
   - Mutants that pass tests → healthy, compete with parent

3. **Competition** — All variants in a lineage compete:
   - Fittest survives, others lose lifespan
   - A mutant that passes tests faster than its parent gains fitness
   - A mutant that fails tests or is slower loses fitness

4. **Culling** — Dead variants are pruned, obituaries emitted

5. **Repeat** — Next cycle mutates the survivors

### Mutation strategy

Not random chaos — **directed by fitness**:

- Functions with high usage are mutated more (they're important, worth improving)
- Functions with inline tests are prioritized (we can measure if a mutation helps)
- Sick functions are healing targets, not mutation targets
- The mutation rate decreases as a lineage stabilizes (if the same variant keeps winning, stop mutating it)

### Auto-seeding

The garden can grow entirely new functions, not just variants of existing ones:

- **Composition**: if `fib` and `print` exist, the garden can try growing `print_fib(n)` that calls both
- **Specialization**: if `sort(list)` exists, the garden can try growing `sort_ints(list)` with a type-specialized body
- **Combination**: if `add(a, b)` and `range(n)` exist, the garden can try growing `sum_range(n)` that combines them

Auto-seeded functions start with inline tests derived from their composition:
- `print_fib(10)` should produce output (test: doesn't crash)
- `sum_range(5)` should return `0 + 1 + 2 + 3 + 4 = 10`

### Growth budget

Evolution isn't free. Each cycle consumes a **growth budget**:

- Budget = 10 + (run_count * 2) — more budget as the garden matures
- Each mutation costs 1 budget
- Each auto-seed costs 3 budget
- When budget is exhausted, the cycle ends
- This prevents runaway growth from filling the veldt with junk

### `veldt evolve` output

```
[EVOLVE] Cycle 1/5
  [MUTATE] fib#2 → fib#3 (constant mutation: 2 → 3)
  [TRIAL]  fib#3 — sick (test fib(10) == 55 failed, got 144)
  [MUTATE] fib#2 → fib#4 (operator mutation: <= → <)
  [TRIAL]  fib#4 — healthy (all tests pass, 0.02s)
  [COMPETE] fib lineage: fib#4 (fitness 2.15) > fib#2 (fitness 2.07)
  [CULL]   fib#1 died — outcompeted (age 12, 0 usage)
  [SEED]   sum_range(n: int) — auto-seeded from add + range
  [TRIAL]  sum_range#1 — healthy (trial: sum_range(5) == 10)
[EVOLVE] Cycle 1 complete: 2 mutations, 1 seed, 1 death
```

### `veldt watch` — continuous evolution

```
veldt watch [--interval N]
```

Runs evolution cycles every N seconds (default 30). The garden evolves in the background while you work. Combined with the IDE, you can watch your code garden grow in real time.

## Part 2: IDE Specification

### Veldt Studio

A dedicated IDE for Veldt — not VS Code with a plugin, but a purpose-built editor where the garden is always visible.

#### Layout

```
┌─────────────────────────────────────────────────────────┐
│  Veldt Studio                              [Evolve] [▶] │
├──────────┬──────────────────────┬────────────────────────┤
│          │                      │                        │
│  GARDEN  │    CODE EDITOR       │     INSPECTOR          │
│  (live)  │                      │                        │
│          │  fn fib(n: int) {    │  fib#2 ◆ healthy       │
│  fib ◆   │    if n <= 1 {       │  age: 8                │
│  ├ #2    │      return n        │  usage: 14             │
│  ├ #3    │    }                 │  fitness: 2.07         │
│  └ #4    │    ...               │  trial: 1.10           │
│          │  }                   │                        │
│  sort    │                      │  lineage: fib          │
│  ├ #1    │  grow fn fib(n: int) │  variants: 3           │
│  └ #2    │    test fib(10)==55  │  fittest: #2           │
│          │  {                   │                        │
│  $pi     │    ...               │  [Trial Run ▶]         │
│  $greet  │  }                   │  [Mutate]              │
│          │                      │  [Prune]               │
│  struct  │                      │                        │
│  Point   │                      │  OBITUARIES:           │
│          │                      │  fib#1 — outcompeted   │
│  [evolve]│                      │  sort#1 — sickness     │
│  [watch] │                      │                        │
├──────────┴──────────────────────┴────────────────────────┤
│  OUTPUT: fib(20) = 6765                                  │
└─────────────────────────────────────────────────────────┘
```

#### Three panels

**Left: Garden panel (live)**
- Tree view of all living code
- Function lineages expand to show variants
- Fittest variant marked with ◆
- Health shown as color: green (healthy), amber (sick), gray (dying)
- Immortal variables ($) and structs shown below functions
- Click a variant → inspector shows details
- Double-click a function → editor jumps to its source
- Bottom buttons: [Evolve] runs one cycle, [Watch] toggles continuous evolution
- Auto-refreshes when the veldt changes on disk

**Center: Code editor**
- Syntax highlighting for .veldt files
- Inline trial results — when you type `grow fn ... test ...`, the editor shows a green checkmark or red X next to the test as you type
- Autocomplete from the veldt — typing `fib(` suggests variants and shows their signatures
- Hover over a function call → tooltip with the variant's health, fitness, and usage
- "Plant" button (▶) runs the current file and grows its code into the veldt
- Error underline for parse/type/runtime errors
- The editor is NOT a file manager — it edits .veldt files, the veldt is the module system

**Right: Inspector panel**
- Selected variant details: health, age, lifespan, usage, fitness, trial score, healing attempts
- Lineage overview: all variants ranked by fitness, fittest highlighted
- [Trial Run] button — re-run the variant's trial and show results
- [Mutate] button — create a mutated variant of the selected function
- [Prune] button — kill the selected variant
- Obituary feed at bottom — recent deaths with causes
- When evolution is running, shows live mutation/trial/competition log

#### Bottom: Output bar
- Program output (print statements)
- Birth/heal/death notifications
- Evolution cycle logs
- Error messages

#### IDE-specific features

**Live trial feedback**: When editing a `grow fn` with inline tests, the IDE runs the tests in the background after each keystroke (debounced). Green check = passing, red X = failing with the error shown inline.

**Garden diff**: After running a program or evolution cycle, the IDE highlights what changed in the garden — new variants (green border), died variants (strikethrough), health changes (color shift).

**Evolution replay**: The IDE can replay an evolution cycle step-by-step, showing each mutation, trial, and competition decision. Useful for understanding why a variant won or died.

**Export**: `veldt export <name>` generates a standalone .veldt file containing the fittest variant of a function — useful for sharing or version control outside the garden.

### Implementation plan

Veldt Studio will be a web application:
- **Backend**: Rust (axum/actix) serving the veldt API + WebSocket for live updates
- **Frontend**: React + the garden visual we already built, extended with a code editor (Monaco/CodeMirror)
- **Real-time**: WebSocket pushes garden changes (births, deaths, evolution events) to the frontend
- **File editing**: Backend reads/writes .veldt files on disk
- **Evolution**: Backend runs evolution cycles in a background thread

## Part 3: Practical Language Features

### The problem

Veldt v0.1 has: int, str, bool, list, structs, functions, if/else, while, for, print, range, len, upper, lower, push. That's enough for fibonacci but not enough to build anything real.

### New types

#### Dict (dictionary/map)

```
let scores = {"alice": 90, "bob": 85}
scores["charlie"] = 78
print(scores["alice"])        # 90
print(len(scores))            # 3
```

- `dict.keys()` → list of keys
- `dict.values()` → list of values
- `dict.has(key)` → bool
- `dict.remove(key)` → remove key

#### Float

```
let pi = 3.14159
let area = pi * r * r
```

- All arithmetic works with floats
- `int` and `float` interoperate: `int + float = float`
- `float.int()` → truncate to int
- `int.float()` → convert to float

### New builtins

#### String operations

```
str.split(sep)        → list of strings
str.contains(sub)     → bool
str.replace(old, new) → string
str.slice(start, end) → substring
str.trim()            → trimmed string
str.chars()           → list of single-char strings
```

#### List operations

```
list.get(i)           → element at index (or null)
list.set(i, val)      → list with element replaced
list.slice(a, b)      → sublist
list.contains(val)    → bool
list.join(sep)        → string (if list of strings)
list.reverse()        → reversed list
list.sort()           → sorted list (integers)
list.map(fn)          → new list with fn applied to each
list.filter(fn)       → new list with elements where fn returns true
list.reduce(fn, init) → accumulated value
```

#### Math

```
math.abs(n)           → absolute value
math.max(a, b)        → maximum
math.min(a, b)        → minimum
math.floor(f)         → floor
math.ceil(f)          → ceiling
math.sqrt(n)          → square root
math.pow(base, exp)   → power
math.random()         → random float [0, 1)
math.randint(a, b)    → random int in [a, b]
```

#### I/O

```
io.read(path)         → string contents of file
io.write(path, str)   → write string to file
io.append(path, str)  → append string to file
io.lines(path)        → list of lines from file
io.exists(path)       → bool
```

#### Type conversion

```
int(str)              → parse string to int
str(n)                → convert any value to string
float(str)            → parse string to float
bool(val)             → convert to bool
```

### Closures and first-class functions

```
let double = fn(x: int) { return x * 2 }
let result = double(5)    # 10

# Pass functions as arguments
let nums = [1, 2, 3]
let doubled = nums.map(fn(x: int) { return x * 2 })
# [2, 4, 6]
```

### String interpolation

```
let name = "world"
let x = 42
print("{name}, the answer is {x}")
# world, the answer is 42
```

### Error handling

```
try {
    let data = io.read("missing.txt")
} catch {
    print("File not found, using default")
    let data = "default"
}
```

### Modules via the veldt

The veldt IS the module system. No imports needed. If you grew `fib` in one program, it's available in every program. But for organization:

```
# Group functions by seeding them with a namespace prefix
grow fn math::sqrt(n: int) { ... }
grow fn str::reverse(s: str) { ... }

# Call with namespace
math::sqrt(16)
str::reverse("hello")
```

Namespaces are just naming conventions — `math::sqrt` is a function named `math::sqrt` in the veldt. The `::` is part of the name, not a separate syntax.

### Practical example: a log analyzer

```
# log_analyzer.veldt — a real program

# Grow utility functions into the veldt
grow fn count_word(text: str, word: str) test count_word("hello world hello", "hello") == 2 {
    let parts = text.split(" ")
    let count = 0
    for part in parts {
        if part == word {
            count = count + 1
        }
    }
    return count
}

grow fn top_words(text: str, n: int) {
    let parts = text.split(" ")
    let counts = {}
    for word in parts {
        if counts.has(word) {
            counts[word] = counts[word] + 1
        } else {
            counts[word] = 1
        }
    }
    # Return the counts dict — the caller can inspect it
    return counts
}

# Use the functions
let log = io.read("server.log")
let word_counts = top_words(log, 10)
for key in word_counts.keys() {
    print(key + ": " + word_counts[key])
}
```

## Implementation priority

1. **Self-growing** (`veldt evolve`, mutations, auto-seeding) — this is the soul of the language
2. **Practical builtins** (string ops, list ops, dict, I/O) — this makes it useful
3. **IDE** (web-based, garden + editor + inspector) — this makes it usable
4. **Closures, string interpolation, error handling** — quality of life

## What makes Veldt good for coding something

Most languages have a package manager. Veldt has a **living ecosystem**. When you write a utility function and grow it, it's there forever — for you, for your other programs, and it evolves. You don't `npm install` a sorting library — you grow `sort`, and if someone grows a better `sort`, yours dies and the better one takes over.

The language is good for:
- **Data processing scripts** — grow reusable parsers, filters, aggregators
- **CLI tools** — grow utility functions that persist and improve
- **Prototyping** — the veldt remembers your helpers across projects
- **Teaching** — watching code evolve and compete makes algorithms tangible
- **Exploration** — `veldt evolve` can discover optimizations you didn't think of

The language is NOT good for:
- **Systems programming** — no manual memory management, no FFI
- **Performance-critical code** — tree-walking interpreter, no JIT
- **Large-scale applications** — no type system beyond basic annotations, no modules beyond the veldt
- **Concurrency** — single-threaded by design
